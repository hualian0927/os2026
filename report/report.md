## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

我对本章的理解是：内核在能够正常启动、访问内存以后，还需要处理打断当前执行流的事件。处理Trap不仅要识别发生了什么，还必须保证C处理函数使用寄存器和栈以后，被中断程序仍能按要求继续执行。

完整流程可以表示为：

```mermaid
flowchart TD
    A[启动并取得DTB信息] --> B[初始化内存管理与内核栈]
    B --> C[设置stvec并进入正常执行]
    C --> D[硬件记录Trap控制状态]
    D --> E[SAVE_ALL建立Trap frame]
    E --> F[__alltraps把当前帧传给trap]
    F --> G[C层分发并处理事件]
    G --> H[RESTORE_ALL读取处理后的帧]
    H --> I[sret决定返回PC和状态]
```

其中我完成的是内存依赖、必要的启动适配，以及从汇编入口到恢复返回的底层模块。图中的C层具体异常和时钟处理由另外两位成员接入。

#### 4.1 功能描述与行为规格

`page_init()`以设备树已经初始化、启动映射和内核栈有效为前提。成功后应设置`va_pa_offset`、`npage`和`pages`，保留固件、内核与描述符占用页，只注册有效范围中的完整空闲页面。零基址或长度、范围溢出和空间不足等错误应在越界写入前panic；没有完整空闲页时不调用注册接口。

Best-Fit的规格是：空闲块头按地址升序排列，`property`表示连续页数，`nr_free`统计页数；申请时遍历全部候选，选最小的足够大块，同大小时选低地址。申请失败不改变状态，释放后正确插入并与物理相邻空闲块合并。

#### 4.2 page_init的关键计算

Lab3没有直接提供实验二使用的边界宏，我依据目标`memlayout.h`计算：

```c
memory_limit    = KERNTOP - PHYSICAL_MEMORY_OFFSET;
kernel_begin_pa = KERNBASE - PHYSICAL_MEMORY_OFFSET;
```

我先检查设备树范围和加法溢出，再将可管理上界限制在框架支持范围内并向下对齐。`va_pa_offset`在第一次使用`PADDR(end)`之前设置；`end`由链接脚本在BSS末尾定义。

```text
描述符起点 = ROUNDUP(PADDR(end), PGSIZE)
描述符数量 = npage - nbase
描述符字节数 = (npage - nbase) × sizeof(struct Page)
空闲区起点 = ROUNDUP(描述符结束物理地址, PGSIZE)
```

`npage`是物理页号的排他上界，不是描述符数组长度。默认128 MiB下，`nbase=0x80000`、`npage=0x88000`，数组有32768个元素。最终空闲页还要扣除保留区域。为防止乘法溢出及空间不足，我在写描述符之前用“剩余空间除以单个描述符大小”的方式校验数量。

描述符先全部设为保留，再交给管理器注册完整空闲区。这样内核和描述符自身占用的页不会被误分配。无完整空闲页的处理只针对`page_init()`，后面的分配器自测仍需要可分配页面。

#### 4.3 Best-Fit与中断保护

| 核心函数 | 本人的理解 |
|----------|------------|
| `best_fit_init()` | 建立空的双向循环链表，将空闲页数置零 |
| `best_fit_init_memmap()` | 将有效保留区域转成空闲块，只把块头挂入链表 |
| `best_fit_alloc_pages()` | 遍历全部块，选最小可用块，移除块头并按需建立剩余块 |
| `best_fit_insert()` | 按地址插入，先合并前块，再以更新后的块头检查后块 |
| `best_fit_free_pages()` | 清理本次归还页的状态，增加本次页数并交给插入合并 |
| `best_fit_nr_free_pages()` | 返回空闲页数，不是块数 |

链表有F个空闲块时，分配查找为O(F)，释放n页并插入合并为O(n+F)，页数查询为O(1)。Best-Fit在这里主要改变选块策略，链表仍保持地址顺序，便于释放时寻找相邻块。

迁移时，我保留了Lab3的`alloc_pages()`、`free_pages()`和`nr_free_pages()`包装：保存原SIE状态，关中断后调用管理器，结束时恢复原状态。原来关着的中断不能被无条件打开。相关宏使用`do { ... } while (0)`把多条语句封装成一条语句，避免在`if/else`等位置展开时改变控制关系。这里保护的是本hart的临界区，不能代替多核锁。

### 功能模块一：Trap上下文恢复与Trap入口

**负责人：2412351－李华濂。**

#### 4.6 模块功能与行为规格

目标文件为`kern/trap/trapentry.S`。我只填写`RESTORE_ALL`、`__alltraps`两个`lab3 function1`位置，保留标记并填写2412351，未改`SAVE_ALL`、结构体、`trap()`签名及题目测试。

```c
void trap(struct trapframe *tf);
```

本模块输入是当前有效的Trap frame。C层正常返回后，汇编应按处理后的帧恢复通用寄存器、返回PC及控制状态，并通过`sret`返回。读完帧之前不能破坏寻址基准；帧内合法的epc或寄存器修改不能被入口旧值覆盖。当前只讨论单hart内核S态，不包含用户栈切换、损坏帧容错和任意嵌套。

#### 4.7 保存布局与原sp

硬件进入S态Trap时记录`sepc/scause/stval`等状态，并调整中断与特权级相关位；通用寄存器则由`SAVE_ALL`保存到内存。RV64的`REGBYTES=8`，帧有36个槽，共288字节。

| 字段 | 槽位 | 字节偏移 |
|------|------|----------|
| x0～x31 | 与寄存器编号一致 | 编号×8 |
| 原sp，也就是x2 | 2 | 16 |
| status | 32 | 256 |
| epc | 33 | 264 |
| badvaddr | 34 | 272 |
| cause | 35 | 280 |

```text
进入前：sp = S
保存后：sp = F = S - 288
传入C： tf = F
帧内：  tf->gpr.sp = S
```

`SAVE_ALL`先把原sp放进`sscratch`，再减sp建立帧，之后将原值取出写入第2槽，同时把`sscratch`清零。由于288是16的倍数，原栈符合ABI对齐时，调用C仍保持16字节对齐。

#### 4.8 传参、C调用与恢复顺序

入口中我使用：

```asm
mv a0, sp
call trap
```

这里传的是当前帧首地址。虽然a0会被改成指针，`call`也会写ra，但原a0和ra此前已经保存，返回时从帧恢复。C函数按调用约定恢复自己的栈，汇编回来后仍使用同一帧进入`__trapret`。

恢复控制状态的关键顺序为：

```asm
LOAD s0, 32*REGBYTES(sp)
LOAD s1, 33*REGBYTES(sp)
csrw sstatus, s0
csrw sepc, s1
# 随后从各自槽位恢复通用寄存器，包括s0和s1
# 最后读取原sp；在此之前sp一直指向帧首
LOAD x2, 2*REGBYTES(sp)
```

先写CSR、再恢复通用寄存器，可以防止CSR临时值覆盖刚恢复的s0/s1。sp必须最后加载，否则后续字段会从错误地址读取。恢复sp采用帧内值，而不是固定加288；x0不用加载，始终为零。`cause/badvaddr`用于诊断，不需要机械写回。

#### 4.9 epc与sret的状态关系

C层需要改变返回位置时应修改`tf->epc`，最终恢复过程会把它写入`sepc`。如果只直接改硬件`sepc`，却不改帧，恢复时仍会被帧内值覆盖。

本场景从S态进入Trap时，保存的`SPP=1`、`SIE=0`、`SPIE=进入前的SIE`。恢复后执行`sret`，由SPP决定返回S态，并使`SIE=SPIE`、`SPIE=1`、`SPP=0`。因此我分别检查这些位的关系，不使用整个`sstatus`前后相等的断言。

恢复期间帧内SIE应保持0；返回后是否开中断通过SPIE表达。若handler提前使能中断，再遇到挂起事件，就可能在恢复未完成时重入，这不属于当前协议保证的场景。

本例特意选择`epc+8`作为后继，跳过断点后的一条4字节非法指令，用于证明恢复服从修改后的帧；这不表示正式异常处理应该统一加8。正式handler仍需按实际异常指令长度和处理策略更新返回位置。

## 六、实验总结与收获

### 6.1 对操作系统的理解

| 重要知识点 | OS原理与本实验的关系 |
|------------|---------------------|
| 中断与异常 | 都需要进入Trap处理路径；中断通常来自异步事件，异常与当前指令有关。本阶段重点实现共用的现场交接，而非全部事件处理 |
| 上下文保存 | 原理上需要保存恢复执行所需的状态；本实验用固定布局的Trap frame保存整数寄存器和四个CSR字段，不等于完整进程上下文切换 |
| 调用约定 | C调用允许覆盖caller-saved寄存器，Trap返回却要恢复被中断现场。因此只遵守普通函数ABI不足以替代Trap保存恢复 |
| 特权级与返回控制 | `sepc`决定返回PC，SPP参与选择返回模式，SIE/SPIE按架构转换；它不是普通`ret`，也不是把状态寄存器原样复制回来 |
| 临界区保护 | 分配器更新共享链表时需要避免本hart中断重入；保存并恢复原状态比无条件开中断更准确，但仍不能解决多核并发 |
| 内存发现与分配 | DTB报告RAM范围，页描述符和保留区处理后才能得到可分配页；物理内存总量不等于空闲页数 |

我认为OS原理中重要、但本阶段没有实际实现的内容包括：进程调度与抢占、用户态陷入时的内核栈切换、系统调用与权限检查、多核锁和内存一致性、嵌套中断策略，以及设备中断控制器和外设驱动。当前Trap frame的恢复也没有覆盖浮点、向量等扩展状态。

### 6.2 AI协作开发的经验

本阶段最有用的做法是先说明接口、状态变化和失败条件，再要求实现。以sp为例，如果只要求“恢复全部寄存器”，很容易忽略读取帧时仍要依赖sp；把原sp、帧sp与C参数的关系写清楚以后，恢复顺序就有了明确依据。

我也认识到测试驱动本身需要审查。题目辅助函数存在callee-saved保护风险，独立驱动因此单独检查自己的ABI。正常用例通过以后，再让两个错误副本接受同一套检查，可以确认测试是否真正观察到了epc和寄存器恢复，而不是只看到一个PASS字符串。

对验证结论，我将真实启动链路、使用替身的独立检查和正式集成分别记录。这样在同伴接入模块二以后，能够明确哪些结论可以沿用，哪些必须在最终版本上重新回归。
